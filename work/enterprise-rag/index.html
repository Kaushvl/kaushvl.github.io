Enterprise RAG & Text-to-SQL

A retrieval system over a messy enterprise corpus, with a natural-language layer that knows when to read documents and when to talk to a database.

Role
Data Scientist · NexusLink
Year
2025
Status
Shipped
Stack
Python · FastAPI · vLLM · LLaMA · Qdrant · PostgreSQL · Oracle Cloud

The problem

Teams across the business were sitting on years of documents, dashboards and operational data in different shapes — PDFs, Confluence pages, ticket histories, structured tables. Answering even a simple question often meant pinging three people and grepping a wiki. The existing search was keyword-based and routinely missed the right document, and nobody wanted to write SQL just to look up a customer.

Goals

  • One natural-language entry point for both unstructured and structured data.
  • Privacy-compliant — no enterprise data leaving our infra.
  • Latency under a second for typical questions, well under five for the heavy ones.
  • Measurable retrieval quality, not just vibes.

Approach

I built the system in three layers — a retrieval layer, a query router, and an inference layer — each one observable and individually swappable.

For retrieval I used hybrid search: dense embeddings in Qdrant for semantic recall, BM25 for exact-match precision, and a reranker on the top 50 candidates to compress that into the final context. Chunking was tuned per source — long-form PDFs into ~700-token overlapping windows with metadata, tickets into single conversations, and tables ingested with column-aware summaries instead of raw rows.

The query router is a small classifier in front of the LLM. It decides, given a question, whether to (a) run RAG over documents, (b) route to the Text-to-SQL/NoSQL path, or (c) do both and merge. This sounds simple but it was the highest-leverage decision in the whole system — most failure modes upstream became "we tried to answer a structured question with documents."

For inference I deployed LLaMA Maverick on Oracle Cloud with vLLM. Self-hosted gave us the privacy guarantees we needed and a predictable cost ceiling. vLLM's paged attention and continuous batching held latency steady as concurrency grew.

The boring infrastructure that made it real

  • FastAPI microservices for retrieval, routing, SQL generation and inference — each independently scalable.
  • Token-aware streaming so the UI starts rendering before the model finishes.
  • A caching layer keyed on question fingerprint + corpus version — the same question twice in five minutes costs us almost nothing.
  • Structured logs going to a small evaluation harness so we can watch retrieval quality drift over time.

Outcomes

~50%
lower query latency
~35%

100%
on-prem inference

What I'd do differently

I'd build the query router first and the RAG pipeline second. Routing is the load-bearing piece, and skipping it forces you to make retrieval do work it was never designed for. I'd also invest in evaluation infrastructure before I felt like I needed to — by the time retrieval quality starts drifting, you want a week of historical data, not a fresh notebook.

The most useful thing a RAG system can do is admit when it shouldn't be doing RAG.
